# workctl → Multica delegation integration research

## Current extension points

* `workctl/internal/workcli/root.go:15-20` builds the executable command tree by taking `cli.NewRoot()` and adding the explicit `linear` group plus `cmdplane.New()`. Linear's compatibility root is built in `workctl/internal/cli/root.go:31-55`; all Linear command constructors are registered in `registerLinearCommands` at `:89-141`. A new delegation command can therefore be added as a sibling service group (for example `multica`) in `workcli.NewRoot`, or as an issue subcommand by adding a constructor to `cmdissue.New` (`workctl/internal/cmdissue/issue.go:22-51`). The latter preserves the natural `workctl issue …` syntax and the former isolates Multica-specific configuration.
* Cobra commands mostly use inline `Run` functions and process-level `os.Exit` after `errors.HandleError` (for example `workctl/internal/cmdissue/issue_more.go:169-249`). For testable new code, keep network/filesystem behavior in a package and make the command a thin adapter; `workcli.Run` (`workctl/internal/workcli/root.go:23-42`) is the cleaner error-returning boundary for end-to-end tests.
* Linear transport is already factored: `workctl/internal/graphql/client.go:25-35` exposes `Client`, `NewClient` (`:99-115`) resolves credentials, and `Request`/`RequestRaw` (`:117-199`) handle auth, JSON, GraphQL errors, and endpoint overrides. A bridge should use this client rather than shelling out to `workctl` or duplicating HTTP. `LINEAR_GRAPHQL_ENDPOINT` and `LINEAR_API_KEY` are test seams (`:45-50`, `:53-97`).
* `workctl/internal/issues/start_update.go:153-179` provides a reusable `issues.UpdateIssue(ctx, id, input map[string]any)` wrapper for arbitrary `IssueUpdateInput` fields. It is the existing seam for assigning a delegate (`{"delegateId": ...}`) and returns the mutation's raw issue payload. `workctl/internal/issues/create.go:17-35` models normal issue creation; it does not expose `DelegateId`, although the generated GraphQL input does (`workctl/internal/gql/generated.go:790-792`) and the schema permits `delegateId` on both create and update (`workctl/graphql/schema.graphql:13883-13888`, `:16861-16867`).
* Existing comment support can persist a handoff or result: `workctl/internal/cmdissue/issue_more.go:39-46` defines `commentCreate`, and `:169-249` accepts `--body`, `--body-file`, and `--reply-to`. A bridge can reuse the same mutation through a package-level helper (rather than parsing command output) to record the Multica issue/task ID and prompt name in a Linear thread.

## Agent/session capabilities already present

* `workctl/internal/cmdissue/issue.go:31-51` registers `agent-session`; `workctl/internal/cmdissue/issue_more.go:817-826` currently exposes only `agent-session list` and `agent-session view`.
* `agent-session list` (`issue_more.go:829-920`) finds sessions through `issue.comments.nodes.agentSession`, supports `--status` and `--json`, but fetches only the first 100 comments and does not follow `pageInfo` despite requesting it (`:847-861`). `agent-session view` (`:922-990`) reads `agentSession(id)` and prints status/type/summary/issue; both commands use raw GraphQL and `os.Exit`.
* The checked-in Linear schema already has the API objects needed for a first-party delegation path: `Issue.delegate` and `Issue.agentSessions` (`graphql/schema.graphql:12789-12823`, `:13012-13018`), `agentSessionCreateOnIssue`, `agentSessionCreate`, and `agentSessionUpdate` mutations (`:17360-17424`), and `agentActivityCreatePrompt` (`:17362-17376`). `AgentSessionCreateOnIssue` accepts an issue identifier (`:771-779`), and `AgentActivityCreatePromptInput` accepts `agentSessionId`, structured prompt content, `queued`, and `sourceCommentId` (`:285-302`). This makes a Linear-native session + prompt possible if the credential has the required agent permissions.
* The schema's `IssueCreateInput.delegateId` and `IssueUpdateInput.delegateId` identify the delegated agent user (`graphql/schema.graphql:13883-13888`, `:16861-16867`). A Multica bridge should treat this as optional metadata: setting `delegateId` alone may not create a runnable external session, while creating a Linear agent session is a separate mutation. Verify the desired Multica workflow against the target API before coupling the two.
* No local worker, subprocess runner, webhook/watch loop, or Multica client exists in workctl. The only process execution is Git branch setup in `workctl/internal/issues/start_update.go:100-115` (`exec.Command("git", ...)`). Therefore a delegation command should be a synchronous handoff (issue lookup → prompt resolution → Multica CLI/API call → Linear comment) and should not claim to monitor completion until a durable worker is added.

## Configuration and local prompt implications

* Linear project config is deliberately small and process-global: `workctl/internal/config/config.go:14-68` loads only `linear.toml` then `.linear.toml` from the current directory, and `GetOption` gives `LINEAR_*` environment variables precedence (`:47-68`). It stores arbitrary string values without schema validation. Do not put multiline agent prompts or Multica credentials in this file.
* Plane has a stricter, separate profile resolver (`workctl/internal/planeconfig/config.go:14-72`, `:174-245`) and explicitly avoids reading Linear state. Reusing Plane config for Multica would violate that isolation. A new `internal/multicaconfig` (or `internal/delegationconfig`) package should own Multica endpoint/profile/token settings.
* Recommended MVP prompt resolution: require an explicit `--prompt-file <path>` or `--prompt <name>`; resolve named prompts relative to the repository at `.workctl/agent-prompts/<name>.md` (or a clearly documented equivalent), then optionally fall back to a user directory such as `$XDG_CONFIG_HOME/workctl/prompts`. Read the file once, reject missing/empty prompts, and pass the exact UTF-8 body to the handoff. Keep local prompt files out of Linear descriptions/comments unless the user explicitly requests a copy. This gives versionable, reviewable prompts without adding secrets to TOML.
* If project config needs a default prompt, add a narrow `[delegation]` table in a new validated config loader rather than extending `config.GetOption`'s untyped map. Suggested fields are `profile`, `prompt`, and `auto_comment`; tokens/endpoints belong in user config or environment. Preserve an explicit `--no-profile`/`--prompt-file` escape hatch so CI can be deterministic.

## Recommended MVP shape

1. Add an `internal/delegation` package with interfaces such as `LinearClient` (issue/session/comment operations), `MulticaClient` (submit handoff), and `PromptResolver`. The production Linear implementation can wrap `graphql.Client`; tests can inject an `httptest` client or fake interfaces. Keep Multica invocation behind an interface so the first adapter can call a configured `multica` executable with `exec.CommandContext` while a future adapter can use an API.
2. Add `workctl issue delegate <issueId>` (or a top-level `workctl multica delegate`) in `cmdissue`. Flags should include `--prompt-file`/`--prompt`, `--agent` or `--profile`, `--multica-command` only if needed, `--comment`/`--no-comment`, and `--json`. Resolve IDs with the existing `linear.IssueIdentifier`/`mustResolveIssue`; fetch issue title/description/url via `linear.FetchIssueDetailsJSON` or a new typed operation; construct a bounded handoff payload; submit it; and print a stable JSON object containing Linear identifier, Multica task/run ID, and prompt name.
3. Make writes idempotent. Before submission, inspect `issue.agentSessions` or a bridge marker in a root comment; if an active handoff already exists, return its ID unless `--force` is supplied. After a successful external submission, add a Linear comment with the Multica task/run link and prompt name. If comment creation fails after submission, report the external ID and return an error rather than retrying the handoff blindly.
4. Add a separate `workctl issue delegate-status <issueId>` only when the bridge has a read API. Until then, `issue agent-session list/view` can display Linear-native sessions, but these are distinct from a Multica run unless the adapter stores the mapping explicitly.

## Tests and validation to add

* Mirror the existing HTTP fixture style in `workctl/internal/cmdissue/issue_test.go:58-107` and `workctl/internal/cmdissue/comment_archive_test.go:14-49`: assert the GraphQL operation/variables (`agentSessionCreateOnIssue`, `agentActivityCreatePrompt`, or `issueUpdate` with `delegateId`), verify auth headers, and return deterministic `data` fixtures.
* Add pure tests for prompt path resolution, empty/missing files, precedence (`--prompt-file` over named/default), path traversal or repository-root behavior, and exact body preservation. Avoid executing a real Multica process in unit tests; inject a fake `MulticaClient` and cover non-zero/unknown-result errors.
* Add command registration/help tests alongside `workctl/internal/cli/root_test.go:22-58` and `workctl/internal/workcli/root_test.go:15-47`. Test `workcli.Run` for validation vs external failures and ensure JSON output preserves field names and nesting, matching the repository's AGENTS.md requirement.
* Run `go test ./...`, `go vet ./...`, and (for bridge packages) `go test -race ./internal/delegation/... ./internal/cmdissue/...`. If GraphQL query documents are added under `internal/gql/queries`, regenerate with `go generate ./internal/gql/` as required by `workctl/AGENTS.md`.

## Main risks

* Linear's agent mutations are marked internal in the schema, and `AgentActivityCreatePromptInput` is also internal; a normal API key may not be authorized. Keep a Multica CLI/API adapter as the primary path and make Linear agent-session creation a capability-gated optional path.
* `agent-session list` currently scans sessions indirectly through comments and does not paginate, so it is not a safe deduplication primitive by itself. Add a direct `issue.agentSessions` query with `pageInfo` or use a deterministic bridge comment marker.
* Existing command handlers call `os.Exit`, which complicates composition and tests. New delegation code should return errors through `RunE`/`workcli.Run`, and only the process boundary should format/exit.
